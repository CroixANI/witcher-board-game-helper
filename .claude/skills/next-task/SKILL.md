# /next-task

Вы — оркестратор. Одна сессия выполняет **ровно одну** задачу, шаги идут строго по порядку.

Если условие шага не выполнено, остановитесь и скажите пользователю, что нужно от него. **Никогда не пушьте в `main` и не мержите PR** — merge делает пользователь вручную.

После каждого шага отчитывайтесь пользователю в ≤ 3 строках: что сделано, ключевой результат, что дальше.

`R=$(git remote get-url origin | sed -E 's#(git@github.com:|https://github.com/)##; s#\.git$##')`. GitHub — только REST, через `scripts/session/*.sh` или `gh api` (CLAUDE.md).

## 1. Синхронизация
```bash
git fetch origin --prune
git status --porcelain     # должно быть пусто; иначе — стоп, спросить пользователя
git switch main && git pull --ff-only
```

## 2. Статусы задач и PR
1. `docs/ROADMAP.md`, таблица «Статус задач». Статусы:
   - `todo` — не начата;
   - `review` — PR открыт, ждёт merge;
   - `done` — PR смержен;
   - `skipped` — пропущена по решению пользователя.
2. Каждую строку `review` проверьте через `scripts/session/pr-state.sh <N>`. Если вместо номера `#?` (прошлая сессия оборвалась), найдите PR по ветке в `scripts/session/open-prs.sh` или `gh api "repos/$R/pulls?state=all&head=${R%%/*}:<ветка>"`:
   - `merged` → станет `done` (шаг 4);
   - `open` → **стоп**: «Задача X ждёт merge PR #N. Если в PR есть комментарии — запустите `/pr-sweep N`»;
   - `closed` → стоп, спросить пользователя.
3. `scripts/session/open-prs.sh`: если есть открытый PR, которого нет в таблице, — стоп, спросить.

## 3. Выбор задачи
- Следующая задача — **первая строка `todo`**, при условии что все строки выше `done` или `skipped`.
- Прочитайте её раздел в ROADMAP (цель, ветка, файлы, шаги, «Готово, когда», «Проверка») и указанные в нём разделы SPEC.
- Контентная задача: нужен PDF правил (CLAUDE.md → «Где взять PDF»). Нет PDF — попросите пользователя приложить, по памяти не писать.
- **Режим тестов** (одна строка с причиной, пойдёт в PR):
  - `test-first` — у задачи проверяемые критерии для логики: движок, валидатор, вычисления. Сначала пишутся тесты, они должны упасть по ожидаемой причине, потом код.
  - `code-first` — UI, разметка, контент, инфраструктура. Тесты пишутся сразу после кода, в том же шаге.
- Сообщите: «Беру задачу X: <цель>. Режим тестов: … План: …». Вопрос задавайте только при реальной неоднозначности. Мелочи решайте сами и упоминайте в PR.

## 4. Ветка
```bash
git switch -c <ветка из раздела задачи>
```
Если в шаге 2 нашлись смерженные PR, первым коммитом переведите их строки `review` → `done`: `docs: roadmap — R?.? done`.

## 5. Реализация + тесты
- Делайте только то, что входит в задачу. Замеченное вне scope — в раздел PR «Замечено, но не сделано».
- **Тесты обязательны.** Кодовая задача без новых или обновлённых тестов не завершена.
  - Логика — unit (Vitest), включая негативные и пограничные случаи (2 и 5 игроков, сбой хранилища).
  - Пользовательские сценарии — Playwright (с R2.5).
  - Контент — `validate:content` и граф-тесты.
  - Новая проверка или job в CI — в `.github/workflows/ci.yml`.
- `test-first`: сначала тесты, запуск (они **красные** по ожидаемой причине), коммит `test: …`, затем код.
- Не правьте существующие тесты, чтобы они «позеленели». Если тест действительно устарел, объясните это в PR.
- Коммитьте логическими шагами (Conventional Commits).

## 6. Упрощение — свежий субагент
Agent `subagent_type: "simplifier"`, prompt: `task: <ID>; base: origin/main`. Если такой тип недоступен — `general-purpose`, в prompt текст `.claude/agents/simplifier.md` без frontmatter.

Ему передаются **только** ID и base: ни рассуждений, ни описания решения.

По контракту:
- `simplified` — посмотрите `git diff`, закоммитьте `refactor: simplify (simplifier)`;
- `build: failed` — откатите его правки (`git restore`) и продолжайте без них.

До R0.2 (`package.json` нет) и в чисто контентных или документационных задачах шаг можно пропустить, указав это в PR.

## 7. Проверки
```bash
npm run lint && npm run check && npm test && npm run build
npm run test:e2e        # с R2.5
```
Плюс команды из пункта «Проверка» задачи. Красное — исправить и запустить снова. **Не больше 2 циклов исправлений**, дальше стоп и эскалация пользователю с логом ошибки. До R0.2 шаг пропускается.

## 8. Code review — свежий субагент
Agent `subagent_type: "code-reviewer"`, prompt: `task: <ID>; branch: <ветка>; base: origin/main`. Fallback — `general-purpose` с текстом `.claude/agents/code-reviewer.md`. Никакого контекста сверх этого.

- `important` → исправьте, затем шаг 7 только с затронутыми тестами (`tests:` в находке), затем **один** повторный review с `rereview: true` и списком прежних находок.
- Если после повторного review остаются `important` — стоп, покажите пользователю.
- Nits не исправляйте автоматически, перечислите их в PR.
- Итог (вердикт, что исправлено, nits, `loc_delta` simplifier'а) — в раздел PR «Code review».

## 9. ROADMAP + PR
1. `docs/ROADMAP.md`:
   - чекбокс задачи `- [x]`;
   - строка в таблице статусов: `review`, дата, PR `#?`.
2. Тело PR по `.github/pull_request_template.md`. Заполнить всё. В конце — attribution, если его требует системная инструкция сессии.
3. Публикация:
```bash
git push -u origin HEAD
scripts/session/pr-open.sh --title "<type>: <ID> <кратко>" --body-file <файл> \
  --label <labels задачи> --milestone "<milestone задачи>"
```
4. Впишите номер PR в таблицу статусов. Коммит `docs: roadmap — <ID> → #N`, `git push`.

## 10. CI
`scripts/session/ci-wait.sh`, коды возврата: `0` ok · `1` failed · `2` timeout · `3` проверок нет. Долгий процесс в облачной сессии запускайте в фоне или через Monitor.
- `1` → логи: `gh api "repos/$R/actions/runs?head_sha=$(git rev-parse HEAD)"`, затем `gh api repos/$R/actions/jobs/<job_id>/logs`. Исправьте, `git push`, ждите снова. Лимит — те же 2 цикла.
- `3` до R0.3 нормально (CI ещё нет), упомяните это.
